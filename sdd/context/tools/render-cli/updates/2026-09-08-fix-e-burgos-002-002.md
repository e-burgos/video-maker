## Estructura

- **`stageForArgument` deja de ser código muerto.** `parse-cli-args.ts` lo cablea al construir los
  errores de argumento: un error de uso **sobre un comando ya reconocido** (`--preset`/`--seed` en
  `ingest|render`, `<project-root>` faltante, positional extra, y los tres errores traducidos de
  `node:util parseArgs`) lleva la etapa de ese comando. El token genérico queda **sólo** para el
  caso en que ni el comando se reconoció — ahí `stage: null` es la verdad.
- **`CliUsageError` acepta `stage` opcional** (`stage?: Stage | null`, default `null`): antes lo
  tenía cableado a `null` como campo de clase.
- **Las seis etiquetas de `formatCliError` son inglesas**: `[usage]`, `[internal]`, `resource:`,
  `expected:`, `cause:`, `hint:`. Con ellas, los `expected`/`hint` que la CLI genera también pasan a
  inglés (`non-negative integer`, `run \`ingest\` before \`plan\``,
  `run \`plan\` before \`render\``, `<command> takes no --preset and no --seed`).

## Qué sigue

- **La línea `cause:` todavía puede traer castellano**, porque su texto **no lo genera la CLI**:
  viene del `message` de los errores de `libs/media-local` y `libs/composition-remotion`
  (`No se encontró el binario "whisper-cli".`, `Remotion no pudo bundlear el entry point.`). La
  etiqueta es inglesa; el contenido es de otro subproyecto. Traducir esos mensajes es un cambio en
  esas libs, no en `render-cli`, y no se hizo acá.
- **Descopado con recomendación escrita:** el tercer follow-up heredado — "el exit code exacto sólo
  se observa invocando el binario, nunca `nx run`" — **no se resuelve con código**. No es un defecto
  de `render-cli` sino el comportamiento de Nx, que normaliza todo fallo de `nx:run-commands` a `1`.
  Ya está capturado donde sirve: como evidencia medida en la spec de `spec-005`, como lección en
  `sdd/memory/lessons.md` y como procedimiento copiable en el README de `apps/render-api`.
  Convertirlo en código agregaría una capa de indirección propia para compensar una limitación de
  la herramienta.
